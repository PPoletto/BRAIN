## TL;DR

- Our server is **hand-rolled JSON-RPC** (no SDK: `src-tauri/Cargo.toml` has no `rmcp`/MCP crate) and speaks the
  **legacy** revision `2024-11-05` (`PROTOCOL_VERSION`), three revisions older than the last legacy one (`2025-11-25`).
- The spec explicitly allows a **dual-era server** ("Legacy client | Dual-era server → Works", Versioning §Compatibility
  Matrix). Nothing forces us to drop `initialize`/`ping`: they are *removed from the modern revision*, not on a
  deprecation clock. The risk is purely client-driven (a client going modern-only).
- A dual-era client probing us on stdio sends `server/discover` and **falls back to `initialize` on any non-modern
  error** (stdio §Backward Compatibility). Our `-32601` answer (0.2) is exactly what makes that fallback work — we must
  **not** answer with a modern code (`-32022`) until we actually serve the modern era.
- The modern delta for a tools-only stdio server is small: per-request `_meta` validation, `server/discover`,
  `resultType` on every result, `ttlMs`/`cacheScope` on `tools/list` + `server/discover`, `serverInfo` in result
  `_meta`. Estimate **S–M (~1 day)**.

## 1. What we implement today (from `server.rs`)

| Area | Today |
|---|---|
| Framing | newline-delimited JSON-RPC 2.0 over stdin/stdout; logs via `tracing` to stderr; exits on EOF + parent watchdog |
| `initialize` | Always answers `protocolVersion: "2024-11-05"` (ignores the client's requested version), `serverInfo {name:"BRAIN", version}`, `capabilities {tools:{listChanged:false}}`; no `instructions` |
| `notifications/initialized` | swallowed like every `id`-less message (no reply); no handshake state is kept |
| `ping` | `{}` |
| `tools/list` | static, deterministic vector of `{name, description, inputSchema}`; no `title`, `annotations`, `outputSchema`; no pagination (`cursor` ignored, no `nextCursor`) |
| `tools/call` | `{content:[{type:"text"}], isError}`; no `structuredContent`; unknown tool → `isError:true` *result* |
| Errors | `-32700` parse, `-32600` non-2.0, `-32601` unknown method, `-32603` handler panic, `-32000` no vault mounted |
| `_meta` | neither read nor written |
| Roots / Sampling / Logging / resources / prompts / elicitation | not implemented |
| Since 0.2 (this slice) | one `info` log line per process with the client's declared version + `clientInfo`; `server/discover` → specific `-32601` |

**What "stdio" means under the stateless model** (stdio binding): framing unchanged (one JSON-RPC message per line, no
embedded newlines, stdout only MCP, stderr free for logs). All metadata travels inline in `params._meta` — "There is no
header layer." The process is **not** a session; clients may interleave unrelated requests. Shutdown = client closes
stdin (server SHOULD exit on EOF — we do); on crash the client SHOULD restart and retry. Cancellation stays
`notifications/cancelled`. Era detection: a dual-era client SHOULD probe `server/discover` first and fall back to
`initialize` on "any other error, or does not respond within a reasonable timeout"; the fallback "MUST NOT be keyed to
one specific error code".

**Deprecation timeline, exactly as the registry states:** Roots, Sampling, Logging, Dynamic Client Registration —
deprecated in `2026-07-28`, earliest removal "First revision released on or after 2027-07-28". `includeContext:
"thisServer"/"allServers"` — follows Sampling. HTTP+SSE transport — deprecated since `2025-03-26`, earliest removal
"Three months after SEP-2596 reaches Final". Policy: minimum window twelve months, measured from the release of the
revision that first marks the feature Deprecated; expedited removal possible for active security risk, but no less than
ninety days. Removal is a Core-Maintainer decision and may come later than the earliest date.
`initialize`/`ping` are **not** in the registry — they are simply absent from the modern revision.

## 3. Where the roadmap's Slice 0 text is wrong or imprecise

1. "jede Anfrage trägt Protokollversion/Client-Info/Capabilities" — version and `clientCapabilities` are MUST, `clientInfo`
   only SHOULD, and all three live in `params._meta` under `io.modelcontextprotocol/*` keys (not as top-level fields).
2. "Listen-Ergebnisse bekommen `resultType`/`ttlMs`/`cacheScope`" — `resultType` goes on **every** result (incl.
   `tools/call`, `server/discover`); `ttlMs`/`cacheScope` go on the list results **and** `resources/read` + `server/discover`.
3. "Roots/Sampling/Logging/HTTP+SSE deprecated (Frist ≥ 12 Monate, frühestens Juli 2027)" — correct for
   Roots/Sampling/Logging; **wrong for HTTP+SSE** (three months after SEP-2596 is Final). Irrelevant for us (stdio).
4. The framing "`initialize` und `ping` entfallen" reads like a deadline. They are removed from the modern era only; a
   dual-era server is explicitly supported and legacy clients keep working against it. There is no spec clock on us.
5. 0.4 "wenn die neue Version verhandelt wurde" — there is no negotiation step; the era is decided **per request** from
   `_meta` (a stdio process MAY serve both eras concurrently).
6. Missing from the roadmap: `notifications/initialized` removal, `-32022` UnsupportedProtocolVersion, `-32602` for
   missing required `_meta`, `serverInfo` in every result's `_meta`, and the probe semantics that make our `-32601`
   answer the *correct* legacy behaviour.
7. Not verifiable from the spec: which version Claude Code / Claude Desktop / Codex send today. The 0.2 log line
   (`mcp: client declared its protocol version`) answers that from real sessions.

**SDK status:** we use no SDK (confirmed). The release post says the Rust SDK supported 2026-07-28 "in beta" at
release; the GitHub releases show `rmcp-v3.5.1` (2026-10-05) with a fix "default missing cache hints for 2026-07-28
peers", i.e. stable 3.x lines handle the modern era. A secondary source (digitalapplied.com, 2026-08-21) reports a
Tier-1 promotion of the Rust SDK — **unverified**. A migration to `rmcp` is not needed for dual-era support (O7).

## 4. Dual-version design (Slice 0.3 — not built)

**Era detection, per request.** `Modern(v)` iff `params._meta["io.modelcontextprotocol/protocolVersion"]` is a string;
otherwise `Legacy`. `initialize` always selects legacy (Versioning: "An `initialize` request selects legacy semantics,
scoped to the stdio process"). No process-level era flag — both eras may interleave.

**Modern request validation (before dispatch):**
- `v` not in `MODERN_VERSIONS = ["2026-07-28"]` → `-32022`, `message "Unsupported protocol version"`,
  `data {supported: MODERN_VERSIONS, requested: v}` (O3).
- `clientCapabilities` missing → `-32602` naming the missing key (spec MUST; O4).
- Method `initialize`, `ping` (or any other legacy-only method) in modern style → `-32601`.

**Responses that change (modern only; legacy stays byte-identical):**
- Every result: add `resultType: "complete"` and `_meta["io.modelcontextprotocol/serverInfo"] = {name:"BRAIN", version}`.
- `tools/list`: add `ttlMs` (O5, proposal `3_600_000` — the list is compiled into the binary and an update restarts the
  process) and `cacheScope: "public"` (no user-specific data).
- `server/discover`: `{resultType, supportedVersions: MODERN_VERSIONS, capabilities: {tools: {listChanged: false}},
  _meta: {serverInfo}, ttlMs, cacheScope: "public"}`; `instructions` optional (O8). Without modern `_meta` it keeps
  today's `-32601` + message, so dual-era clients that probe *without* our version still fall back cleanly.
- `tools/call`: payload unchanged (`content`, `isError`) + the common fields. `brain_ping` stays a **tool** and keeps its
  pre-vault fast path in both eras; only the protocol-level `ping` method is legacy-only.
- `notifications/initialized` (and every other notification): unchanged — still swallowed, never answered. Modern
  clients simply do not send it; there is no handshake state to drop.

**Code shape.** Split `handle_request` into (a) era detection/validation, (b) dispatch returning an internal
`Reply::{Result(Value), Error{code,msg,data}, None}` and (c) one serializer that decorates modern results. `call_tool`
and the tool arms stay untouched. Keep the 0.2 `client_declaration` logger; add the era to the log line.

**Tests that pin the behaviour** (one assertion each, sentence names per CLAUDE.md):
1. legacy `initialize` response is byte-identical to today (`2024-11-05`, no `resultType`);
2. legacy `tools/list` has no `resultType`/`ttlMs`/`cacheScope`;
3. modern `tools/list` has `resultType "complete"`, integer `ttlMs >= 0`, `cacheScope "public"`, `_meta.serverInfo`;
4. modern `tools/call brain_ping` answers without a vault and carries `resultType`;
5. modern `server/discover` returns `supportedVersions` containing `2026-07-28` and `capabilities.tools`;
6. `server/discover` without modern `_meta` keeps the legacy `-32601` message (fallback path);
7. modern request with `"1900-01-01"` → `-32022` with `data.supported` and `data.requested`;
8. modern request missing `clientCapabilities` → `-32602`;
9. modern `ping` → `-32601`, legacy `ping` → `{}`;
10. `initialize` then a modern `tools/list` in the same process are both served (interleaving);
11. notifications (incl. `notifications/initialized`) still yield zero bytes in both eras.

**Effort:** **S–M**, ≈ 1 day: ~150–250 LOC in `server.rs` + 11 tests; +0.5 day if O6 (unknown tool → `-32602`) is included.
